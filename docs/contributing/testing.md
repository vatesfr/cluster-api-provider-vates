# Testing

Two suites guard the provider, and they answer different questions:

| Suite | Command | Environment | Answers |
|---|---|---|---|
| Unit / integration | `make test` | envtest (a real API server + etcd) | Does the logic behave? |
| End-to-end | `make test-e2e` | an isolated kind cluster | Does the controller run in a cluster? |

Both are written with [Ginkgo](https://onsi.github.io/ginkgo/) and
[Gomega](https://onsi.github.io/gomega/), the BDD-style frameworks the Cluster
API ecosystem uses.

## Unit tests and envtest

```bash
make test
```

The target first regenerates and formats the code (`manifests`, `generate`,
`fmt`, `vet`) and downloads the envtest binaries, then runs every package except
`test/e2e`. `envtest` is the important part: it starts a **real Kubernetes API
server and etcd** on the fly, so the tests speak to actual CRDs with actual
validation — no cluster and no kubeconfig required.

`internal/controller/suite_test.go` sets it up. It installs two CRD sets into the
test environment:

- this provider's CRDs from `config/crd/bases`;
- Cluster API's own CRDs, resolved from the Go module cache
  (`sigs.k8s.io/cluster-api@v1.13.1/config/crd/bases`).

The environment is started once in `BeforeSuite`, shared through a package-level
`k8sClient`, and torn down in `AfterSuite`. Run `make setup-envtest` beforehand if
you invoke the tests from an IDE, so the binaries exist and `KUBEBUILDER_ASSETS`
can point at them.

!!! tip "Logic that needs no API server"

    Most of the interesting code does not need envtest at all. The helpers under
    `internal/controller/xomachine/` (IPAM rendering, address handling, disk
    selection, name building) and `internal/bootstrap/` are plain functions with
    tests of their own. Reach for envtest only when the behaviour depends on
    Kubernetes objects.

## The Ginkgo / Gomega style

The suites read as specifications. A typical test nests `Describe` → `Context` →
`It`, labels steps with `By`, and asserts with `Expect` or, for asynchronous
facts, `Eventually`:

```go
var _ = Describe("DefaultVMName", func() {
    It("names the VM after the distribution of the bootstrap configuration", func() {
        name := DefaultVMName("TalosConfig", "my-cluster", true, "my-cluster-cp-4hgx7")
        Expect(name).To(Equal("TALOS-my-cluster-CP-4hgx7"))
    })
})
```

Two helpers appear throughout:

- **The fake client** — `sigs.k8s.io/controller-runtime/pkg/client/fake` builds an
  in-memory client seeded with the objects a test needs (a `Cluster`, an
  `XOCluster`, a `Secret`). Use it to drive a reconciler without envtest.
- **Generated mocks** — the Xen Orchestra interfaces are mocked with
  `go.uber.org/mock/gomock`. The mocks are regenerated by the `//go:generate`
  directives in `internal/controller/doc.go` and let a test assert exactly which
  XO calls were made.

!!! note "Prefer several focused `It` blocks"

    The convention here is one behaviour per `It`, with small helper
    constructors to keep each case short, rather than a single large
    table — read `internal/bootstrap/build_test.go` and
    `internal/controller/xomachine/vm_ops_disk_test.go` for the pattern.

## End-to-end tests

```bash
make test-e2e
```

This target is heavier and more opinionated:

1. `setup-test-e2e` creates an **isolated kind cluster** named
   `vates-capi-test-e2e` if it does not exist.
2. It regenerates the manifests and runs the suite with the `e2e` build tag:
   `go test -tags=e2e ./test/e2e/ -v -ginkgo.v`.
3. `cleanup-test-e2e` deletes the kind cluster afterwards.

!!! warning "The e2e suite requires `docker`"

    The suite's `BeforeSuite` builds the manager image with
    `CONTAINER_TOOL=docker` hardcoded and loads it into kind. On a machine that
    only has podman, install docker for this target (or run the suite in the
    DevContainer) — otherwise the image build fails before any test runs.

The suite (`test/e2e/`) installs cert-manager (skip with
`CERT_MANAGER_INSTALL_SKIP=true`), disables `kubectl` kuberc for isolation
(enable with `KUBECTL_KUBERC=true`), deploys the controller into `capi-system`,
and asserts the manager pod is running and serving metrics. It does **not** need
Xen Orchestra: the credentials secret holds a dummy token, and the tests exercise
the control plane of the provider rather than a real VM.

!!! note "The Cilium addon has its own harness"

    `hack/e2e-cilium.sh` tests the Cilium `CNI` addon against two throwaway kind
    clusters (a management one and a workload one), with no Xen Orchestra at all.
    It renders the manifest through a `ClusterResourceSet` exactly as a real
    cluster would. See the script header for the `MODE`, `CONTROL_PLANE` and
    `KUBECTL_*` knobs.

## Writing a test for a new reconciliation path

Take the smallest environment that can reproduce the branch.

1. **Pure logic?** Add a test next to the function. Construct the input structs,
   call the helper, and assert the result — no client needed.
2. **Needs Kubernetes objects?** Build a fake client with the objects the path
   reads, stub the XO calls with gomock, call `Reconcile`, then assert the
   object's `status.conditions` and `status` fields. Set
   `newClientFunc` on the reconciler to return your mock client.
3. **Needs API validation or the real contract types?** Add a Ginkgo spec to the
   envtest suite, create the CR through `k8sClient`, and drive it.

A good new-path test makes the *observable* promise, not the implementation. For
example: "when `addressesFromPools` is set and the claim is unanswered, the
machine is not created and its `Ready` condition is `WaitingForAddress`" — that
is the behaviour a future refactor must preserve.
